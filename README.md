
# Project Task Manager

## Опис проєкту

Java-проєкт для роботи з проєктними задачами: зберігання, пошуку, перевірки та обміну даними у форматі CSV.

**Предметна область:** проєктні задачі
**Варіант:** 22
**Лабораторна робота:** №5
**Java:** 21
**Система збірки:** Maven
**Версія:** 5.0.0

У лабораторній роботі №5 реалізовано узагальнений репозиторій, а також універсальний CSV-експорт та імпорт на основі Java Reflection і анотації `@CsvColumn`.

Попередню доменну модель, функціональність попередніх лабораторних робіт і старі тести збережено.

## Мета лабораторної роботи

- Реалізувати узагальнений клас `Repository<T>`.
- Забезпечити додавання, отримання знімка та пошук елементів за `Predicate<T>`.
- Створити анотацію `@CsvColumn` для позначення полів, що беруть участь у CSV-обміні.
- Реалізувати універсальний CSV-експорт через Reflection.
- Реалізувати імпорт CSV у типізовані Java-об'єкти.
- Обробляти помилки формату та файлові помилки.
- Перевірити роботу компонентів автоматичними тестами.
- Зберегти сумісність із попередніми лабораторними роботами.

## Структура даних лабораторної №5

Для нової CSV-функціональності використовується клас `ProjectTaskRecord`.

Він містить такі поля:

| Поле | Тип | Заголовок CSV |
|---|---|---|
| `name` | `String` | `назва` |
| `assignee` | `String` | `виконавець` |
| `estimatedHours` | `double` | `години` |
| `status` | `TaskStatus` | `статус` |
| `priority` | `TaskPriority` | `пріоритет` |

Поля, які потрібно експортувати, позначаються анотацією `@CsvColumn`.

Приклад:

```java
@CsvColumn("назва")
private String name;

@CsvColumn("виконавець")
private String assignee;
```

Заголовки CSV формуються зі значень анотації. Порядок колонок детермінований: поля сортуються за назвами Java-полів.

## Перелічувані типи

### TaskStatus

Можливі значення статусу задачі:

- `TODO`
- `IN_PROGRESS`
- `DONE`

### TaskPriority

Можливі значення пріоритету:

- `LOW`
- `MEDIUM`
- `HIGH`

Під час імпорту значення enum перетворюються на відповідні константи Java. Невідоме значення спричиняє помилку формату CSV.

## Узагальнений репозиторій

Клас `Repository<T>` забезпечує типобезпечне зберігання об'єктів.

Основні методи:

- `add(T item)` — додає елемент до репозиторію;
- `snapshot()` — повертає незмінний знімок поточного набору елементів;
- `search(Predicate<T> predicate)` — шукає елементи за заданою умовою;
- `size()` — повертає кількість елементів;
- `isEmpty()` — перевіряє, чи репозиторій порожній.

Приклад використання:

```java
Repository<ProjectTaskRecord> repository =
        new Repository<>();

repository.add(new ProjectTaskRecord(
        "Розробити API",
        "Іван",
        12.5,
        TaskStatus.IN_PROGRESS,
        TaskPriority.HIGH
));

var results = repository.search(
        task -> task.getPriority() == TaskPriority.HIGH
);
```

Клас працює з узагальненим типом `T`, тому логіка репозиторію не прив'язана до конкретного класу задачі.

## CSV-анотація

`CsvColumn` — анотація, яка позначає поля для експорту та імпорту.

Вона має зберігатися під час виконання програми, щоб Reflection могла отримати її значення.

Значення анотації використовується як назва колонки CSV.

Поля без `@CsvColumn` не включаються до CSV-схеми.

## CSV-експорт

Клас `CsvExporter` виконує універсальний експорт списку об'єктів у файл CSV.

Основний метод:

```java
export(List<T> items, Path path)
```

Експортер використовує Reflection для отримання анотованих полів, а не окремі правила для кожного класу предметної області.

Основні характеристики:

- робота з полями, позначеними `@CsvColumn`;
- визначений порядок колонок;
- заголовки беруться з анотацій;
- запис у файл через `Path` та `Files`;
- кодування UTF-8;
- екранування ком, подвійних лапок і переносів рядків;
- підтримка порожнього набору записів.

Для порожнього набору створюється порожній CSV-файл без записів.

## CSV-імпорт

Клас `CsvImporter` читає CSV-файл і перетворює записи на об'єкти заданого типу.

Основний метод:

```java
importFile(Path path, Class<T> type)
```

Під час імпорту перевіряються заголовки та кількість полів. Значення перетворюються на відповідні типи Java, зокрема числові значення та enum.

Парсер підтримує:

- поля, що містять коми;
- подвійні лапки всередині поля;
- переноси рядків усередині лапок;
- порожній файл;
- перевірку структури записів.

Для створення об'єктів використовується Reflection та конструктор, параметри якого відповідають полям CSV-моделі.

## Обробка помилок

Для помилок CSV передбачено `CsvFormatException`.

Виняток має конструктори для повідомлення про помилку та для повідомлення разом із початковою причиною:

```java
CsvFormatException(String message)

CsvFormatException(String message, Throwable cause)
```

Це дає змогу зберігати початкову причину файлової або рефлексивної помилки.

Тестами перевіряються, зокрема:

- неправильна кількість полів;
- некоректне числове значення;
- невідоме значення enum;
- незакриті лапки;
- помилки читання або запису файлів;
- поля з переносами рядків.

## CSV-формат

Для нової функціональності лабораторної №5 використовується CSV із комою як роздільником і заголовками з `@CsvColumn`.

Приклад структури:

```csv
виконавець,години,назва,пріоритет,статус
Іван,12.5,Розробити API,HIGH,IN_PROGRESS
Олена,8.0,Створити дизайн,MEDIUM,TODO
Андрій,5.5,Написати тести,LOW,DONE
```

Порядок колонок визначається назвами Java-полів. У наведеному прикладі порядок такий: `assignee`, `estimatedHours`, `name`, `priority`, `status`.

CSV-експорт екранує спеціальні символи за правилами CSV.

**Важливо:** новий CSV-формат лабораторної №5 не замінює старий формат із крапкою з комою, який використовує попередня функціональність. Старий формат та його парсер збережено для сумісності.

## Рівність об'єктів

У `ProjectTaskRecord` реалізовано `equals()` та `hashCode()`.

Логічна ідентичність задачі визначається комбінацією:

- `name`;
- `assignee`.

Для окремої перевірки ідентичності передбачено метод `hasSameIdentity(ProjectTaskRecord other)`.

Тести перевіряють рівність об'єктів та узгодженість `equals()` і `hashCode()`.

## Тестування

Тести лабораторної №5 зосереджені в `CsvRepositoryTest`.

Вони перевіряють:

- додавання елементів у `Repository<T>`;
- пошук через `Predicate<T>`;
- незмінність знімка репозиторію;
- відхилення недопустимих значень;
- експорт та імпорт;
- збереження ком, лапок і переносів рядків;
- порядок заголовків;
- порожній файл;
- неправильну кількість полів;
- некоректне число;
- некоректний enum;
- незакриті лапки;
- обробку файлових помилок;
- `equals()` та `hashCode()`.

Під час останньої локальної перевірки:

```text
Tests run: 63, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

SpotBugs також завершився без зауважень:

```text
BugInstance size is 0
Error size is 0
No errors/warnings found
```

Ці результати стосуються останнього локального запуску `./mvnw -B clean verify`. Результати GitHub Actions потрібно перевірити окремо після push.

## Continuous Integration

Для проєкту налаштовано GitHub Actions.

Матриця збірки охоплює:

- Ubuntu;
- Windows;
- macOS.

Для всіх платформ використовується Java 21.

На Windows запускається:

```powershell
.\mvnw.cmd -B clean verify
```

На Ubuntu та macOS:

```bash
./mvnw -B clean verify
```

Workflow також завантажує JAR як артефакт для кожної операційної системи.

Налаштування CI розташоване у файлі:

```text
.github/workflows/ci.yml
```

Локальна успішна збірка не замінює перевірку статусу GitHub Actions: перед завершенням роботи необхідно переконатися, що всі три завдання CI завершилися успішно.
