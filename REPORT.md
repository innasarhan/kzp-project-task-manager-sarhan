## 3. Стан до і після лабораторної роботи

### 3.1. Стан до рефакторингу

У лабораторній роботі №2 створено нову доменну сутність `ProjectTask`.

    title
    assignee
    estimateHours
    priority
    done

Поля оголошено як:

    private final

Робоча логіка програми тепер використовує:

## 4. Клас-сутність ProjectTask

### 4.1. Поля класу

Клас `ProjectTask` містить п'ять приватних незмінних полів:

    private final String title;
    private final String assignee;
    private final double estimateHours;
    private final int priority;
    private final boolean done;

Використання `private` забезпечує інкапсуляцію стану об'єкта та обмежує прямий доступ до його полів.

Використання `final` не дозволяє перепризначити поля після створення об'єкта.

### 4.2. Інваріанти

Конструктор `ProjectTask` перевіряє такі умови:

- `title` не повинен бути `null`;
- `title` не повинен бути порожнім або складатися лише з пробілів;
- `assignee` не повинен бути `null`;
- `assignee` не повинен бути порожнім або складатися лише з пробілів;
- `estimateHours` не може бути від'ємним;
- `priority` не може бути від'ємним.

Для перевірки `null` використовується:

    Objects.requireNonNull(...)

Для перевірки порожнього або пробільного тексту використовується:

    isBlank()

Таким чином, некоректний об'єкт `ProjectTask` не може бути створений і не може потрапити до списку задач.

### 4.3. Методи читання

Для доступу до стану об'єкта реалізовано:

    getTitle()
    getAssignee()
    getEstimateHours()
    getPriority()
    isDone()

Setter-методи не використовуються, оскільки стан об'єкта після створення не повинен змінюватися неперевіреними значеннями.

### 4.4. Метод toString

Для класу `ProjectTask` реалізовано метод `toString()`.

Для форматування дробового значення використовується:

    Locale.ROOT

Це забезпечує однаковий формат дробових чисел незалежно від локальних налаштувань операційної системи.

## 5. Фабричний метод fromCsv та record

### 5.1. Статичний фабричний метод fromCsv

Для створення об'єкта `ProjectTask` з одного CSV-рядка реалізовано:

    public static ProjectTask fromCsv(String csvLine)

Формат вхідного рядка:

    title;assignee;estimateHours;priority;done

Метод `fromCsv` виконує:

1. перевірку наявності рядка;
2. перевірку кількості полів;
3. виділення текстових значень;
4. перетворення `estimateHours` у `double`;
5. перетворення `priority` у `int`;
6. перевірку значення `done`;
7. створення об'єкта `ProjectTask`.

Інваріанти самого об'єкта перевіряються конструктором `ProjectTask`.

Такий поділ дозволяє не дублювати правила валідації між фабрикою та класом-сутністю.

### 5.2. Оновлення TaskParser

`TaskParser` тепер відповідає за:

- читання CSV-файлу;
- проходження рядків;
- визначення номера поточного рядка;
- виклик `ProjectTask.fromCsv`;
- додавання лише валідних об'єктів до списку;
- перехоплення `IllegalArgumentException`;
- виведення номера рядка та причини помилки.

Помилка одного CSV-запису не припиняє обробку наступних записів.

### 5.3. Record EstimatePriority

Для представлення пари значень оцінки та пріоритету створено:

    public record EstimatePriority(
            double estimateHours,
            int priority) {
    }

`EstimatePriority` є незмінним допоміжним значенням.

Для `record` Java автоматично створює:

- конструктор;
- accessors `estimateHours()` та `priority()`;
- `equals()`;
- `hashCode()`;
- `toString()`.

У лабораторній роботі перевірено accessors та рівність об'єктів `EstimatePriority`.

## 11. Відповіді на контрольні питання

### 1. Яку проблему розв'язує клас-сутність порівняно з рядком і паралельними змінними?

Клас-сутність об'єднує дані та правила їх коректності в одному об'єкті. Це зменшує ризик розсинхронізації паралельних змінних і дозволяє працювати з предметною сутністю як з одним значенням.

### 2. Що означають `private` і `final` у полях класу?

`private` обмежує прямий доступ до поля ззовні класу. `final` не дозволяє перепризначити поле після завершення конструктора.

### 3. Що таке інкапсуляція і яку проблему вона запобігає?

Інкапсуляція приховує внутрішній стан об'єкта та надає доступ до нього через визначені методи. Вона запобігає неконтрольованій зміні внутрішнього стану.

### 4. Чому перевірку інваріантів розміщують у конструкторі?

Тому що конструктор є місцем створення об'єкта. Якщо перевірити умови там, не можна створити об'єкт у відомо некоректному стані.

### 5. Чим `Objects.requireNonNull` відрізняється від `isBlank`?

`Objects.requireNonNull` перевіряє, що посилання не є `null`. `isBlank()` перевіряє, чи рядок порожній або складається лише з пробільних символів.

### 6. Чому відсутність сеттерів може допомогти зберегти коректний стан?

Без публічних сеттерів після створення не можна довільно змінити поля. Це допомагає зберегти інваріанти, перевірені конструктором.

### 7. Які методи й властивості автоматично отримує `record`?

Для компонентів `record` Java автоматично створює canonical constructor, accessor-методи з назвами компонентів, а також `equals()`, `hashCode()` і `toString()`.

### 8. Чим `record` відрізняється від звичайного класу-сутності?

`record` призначений насамперед для компактного представлення незмінного набору значень і автоматично надає стандартні методи значення. Звичайний клас дає більше свободи для структури, поведінки та власних правил.

### 9. Чому `record` не гарантує глибоку незмінність змінного списку?

`record` робить фінальним саме посилання на компонент. Якщо компонентом є змінний список, його елементи все одно можуть змінюватися.

### 10. Для чого потрібен статичний фабричний метод `fromCsv`?

Він централізовано перетворює один CSV-рядок на коректний об'єкт `ProjectTask` і відокремлює формат входу від основної логіки програми.

### 11. Де потрібно перехоплювати помилку розбору одного рядка?

На рівні циклу читання, де відомий номер поточного рядка. У нашій реалізації це робить `TaskParser`.

### 12. Чому неправильний запис не можна додавати до списку до завершення перевірки?

Тому що невалідний об'єкт може спотворити статистику або порушити інваріанти програми. Спочатку запис потрібно повністю перевірити, а вже потім додавати.

### 13. Яке призначення `toString` і чому він не замінює формат CSV?

`toString()` дає зручне текстове представлення об'єкта для читання та діагностики. Він не повинен замінювати CSV-формат, який є окремим форматом обміну даними.

### 14. Навіщо використовувати `Locale.ROOT` у `toString` і звіті?

Щоб форматування чисел було стабільним і не залежало від локальних налаштувань операційної системи.

### 15. Що означає схема тесту AAA?

AAA — це Arrange, Act, Assert: підготувати дані та стан, виконати дію, перевірити очікуваний результат.

### 16. Які негативні випадки потрібно перевірити для конструктора?

Для `ProjectTask` перевіряються `null`, порожні або пробільні `title` і `assignee`, а також від'ємні `estimateHours` і `priority`. Окремо перевірено граничне значення `0`.

### 17. Як довести, що рефакторинг не змінив зовнішню поведінку попередньої роботи?

Потрібно порівняти вихідні дані та метрики до і після рефакторингу. У цій роботі контрольні значення залишилися: 3 валідні задачі, 26.00 годин, середній пріоритет 2.00 і 2 виконані задачі.

### 18. Чому тести попередньої роботи мають проходити після цієї роботи?

Тому що рефакторинг має змінювати внутрішню структуру, а не ламати вже перевірену функціональність.

### 19. Які файли інфраструктури переносяться з попередньої роботи без повторного створення?

Зберігаються Maven Wrapper, `pom.xml`, GitHub Actions workflow та інші файли інфраструктури, які забезпечують однакову збірку, тестування й пакування проєкту.

### 20. Який рядок реалізації найкраще демонструє інкапсуляцію і чому?

Наприклад, `private final String title;`. Поле приховане від прямого доступу, а його значення після створення об'єкта не можна перепризначити.
