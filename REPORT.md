## 2. Мета роботи та стан продукту

### Мета

Метою лабораторної роботи є освоєння потокової обробки колекцій у Java за допомогою Stream API та заміна частини циклової обробки даних на декларативні потокові операції.

Основні завдання:

- виконати обробку поліморфної колекції `ProjectTask`;
- реалізувати окремі іменовані Stream API-запити;
- використати `filter`, `map`, `groupingBy` та статистичні колектори;
- реалізувати сортування та отримання top-N елементів;
- використати `Optional` для пошуку;
- зберегти існуючий формат CSV;
- зберегти формат контрольного звіту;
- перевірити еквівалентність циклової та потокової реалізацій;
- додати тести для позитивних, граничних та негативних випадків.

### Стан продукту

Після виконання лабораторної роботи:

- доменна модель збережена;
- використовується абстрактний тип `ProjectTask`;
- присутні підтипи `DevelopmentTask` і `TestingTask`;
- використовується `TaskKind`;
- основні статистичні обчислення реалізовано через Stream API;

## 3. Стан «до / після»: заміна циклів на Stream API

У попередній реалізації основні статистичні показники обчислювалися за допомогою циклів.

Клас `TaskMetrics` містить циклову реалізацію:

- сумарної оцінки годин;
- середнього пріоритету;
- кількості виконаних задач.

У лабораторній роботі №4 було створено клас `StreamTaskMetrics`, у якому ті самі показники реалізовано за допомогою Stream API.

### До

Для обходу колекції використовувалися конструкції `for`, накопичення значень та ручна перевірка умов.

### Після

Використовуються потокові операції:

- `mapToDouble(...).sum()`;
- `mapToInt(...).average()`;
- `filter(...).count()`.

Додатково створено клас `ProjectTaskQueries`, який містить окремі іменовані методи для п'яти основних запитів лабораторної роботи.

Вхідна колекція не змінюється під час обробки. Результати формуються як нові колекції, мапи або статистичні об'єкти.

## 4. Контракт даних та доменна модель

Для лабораторної роботи збережено попередню предметну область «Проєктні задачі».

Основним типом є абстрактний клас `ProjectTask`.

Від нього успадковуються:

- `DevelopmentTask`;
- `TestingTask`.

Також для визначення типу задачі використовується enum `TaskKind` зі значеннями `DEVELOPMENT` та `TESTING`.

### Основні поля ProjectTask

- `title` — назва задачі;
- `assignee` — відповідальна особа;
- `estimateHours` — оцінка задачі в годинах;
- `priority` — початковий пріоритет;
- `done` — ознака виконання.

### Валідація

Під час створення задачі перевіряються:

- ненульове значення назви;
- непорожня назва;
- ненульове значення відповідальної особи;
- непорожня відповідальна особа;
- скінченність оцінки годин;
- невід'ємність оцінки годин;
- невід'ємність початкового пріоритету.

### Поліморфізм

Кожен підтип реалізує метод `evaluatePriority()` по-своєму.

`DevelopmentTask` враховує оцінку задачі, а `TestingTask` враховує її стан виконання.

Тому обробка колекції може виконуватися через спільний тип `ProjectTask` без перевірок конкретного підтипу через `if`, `instanceof` або `switch`.

## 5. П'ять основних Stream API-запитів

У класі `ProjectTaskQueries` реалізовано п'ять окремих іменованих методів.

### 5.1. Filter — незавершені задачі

Метод `unfinishedTasks(List<ProjectTask> tasks)` використовує `filter(task -> !task.isDone())`.

Джерело: `List<ProjectTask>`.

Результат: `List<ProjectTask>`.

Метод повертає тільки задачі, які ще не виконані.

### 5.2. Map — отримання назв задач

Метод `taskTitles(List<ProjectTask> tasks)` використовує `map(ProjectTask::getTitle)`.

Джерело: `List<ProjectTask>`.

Результат: `List<String>`.

Об'єкти задач перетворюються на їхні назви.

### 5.3. GroupingBy — групування за відповідальною особою

Метод `hoursByAssignee(List<ProjectTask> tasks)` використовує `Collectors.groupingBy` разом із `Collectors.summingDouble`.

Ключ групування: `String`, тобто ім'я відповідальної особи.

Значення: `Double`, тобто сумарна кількість годин задач відповідальної особи.

Результат: `Map<String, Double>`.

### 5.4. Статистичний запит

Метод `estimateStatistics(List<ProjectTask> tasks)` використовує `Collectors.summarizingDouble(ProjectTask::getEstimateHours)`.

Результат: `DoubleSummaryStatistics`.

Статистика містить:

- кількість елементів;
- суму;
- середнє значення;
- мінімальне значення;
- максимальне значення.

Для порожнього списку метод повертає порожній `DoubleSummaryStatistics`.

### 5.5. Top-N — задачі з найвищим пріоритетом

Метод `topByPriority(List<ProjectTask> tasks, int n)` виконує послідовність `stream → sorted → limit → List`.

Сортування виконується складеним компаратором.

Основний критерій — результат `ProjectTask::evaluatePriority`.

Напрямок основного сортування — за спаданням за допомогою `reversed()`.

Другий критерій — `ProjectTask::getEstimateHours`, за зростанням.

Після сортування використовується `limit(n)`.

Для від'ємного `n` генерується `IllegalArgumentException`.

## 6. Групування та статистика

Для групування використовується `Collectors.groupingBy`.

Ключем є `assignee`, а агрегатом — сума `estimateHours`.

Тип результату: `Map<String, Double>`.

Для статистичного запиту використовується `Collectors.summarizingDouble`, що дозволяє отримати кількість, суму, середнє, мінімум та максимум.

### Порожній ввід

Для порожньої колекції:

- групування повертає порожню `Map`;
- список назв є порожнім;
- список незавершених задач є порожнім;
- `DoubleSummaryStatistics` має `count = 0`;
- середнє значення становить `0.0`;
- сума становить `0.0`;
- мінімальне та максимальне значення мають стандартні граничні значення `DoubleSummaryStatistics`.

### Форматування

Контрольний звіт продовжує використовувати існуючий формат.

Числові значення годин та середнього пріоритету виводяться з двома знаками після крапки, наприклад `26.00` та `2.00`.

Формат звіту не змінювався, оскільки він є частиною зовнішнього контракту попередніх лабораторних робіт.

## 7. Comparator та top-N

Для запиту `topByPriority` використовується складений компаратор.

### Основний критерій

Обчислений поліморфний пріоритет `ProjectTask::evaluatePriority`.

### Напрямок

Пріоритет сортується за спаданням за допомогою `reversed()`.

Тобто задачі з більшим пріоритетом знаходяться на початку результату.

### Другий критерій

При однаковому пріоритеті використовується оцінка часу `ProjectTask::getEstimateHours`.

Вона сортується за зростанням.

### Обмеження

Після сортування використовується `limit(n)`, тому повертається не більше `n` задач.

Перевірено випадки:

- `n = 0`;
- `n < кількості задач`;
- `n > кількості задач`;
- `n` дорівнює кількості задач;
- від'ємне `n`;
- однакові значення основного критерію;
- дублікати задач.

## 8. Пошук через Optional

Окремий метод `findByTitle(List<ProjectTask> tasks, String title)` виконує пошук задачі за назвою.

Використовуються операції `filter(...)` та `findFirst()`.

Результат має тип `Optional<ProjectTask>`.

### Якщо задача знайдена

`Optional` містить відповідний об'єкт `ProjectTask`.

### Якщо задача відсутня

Повертається `Optional.empty()`.

Також перевіряється випадок, коли вхідна колекція порожня.

Окремо перевірено випадок із декількома задачами з однаковою назвою: повертається перша знайдена задача.

## 9. Еквівалентність «цикл → Stream API → результат»

Для контролю правильності результатів збережено попередню циклову реалізацію `TaskMetrics` та створено потокову реалізацію `StreamTaskMetrics`.

| Циклова реалізація | Stream API | Результат |
|---|---|---|
| `for` + накопичення `estimateHours` | `mapToDouble(...).sum()` | однакова сума |
| `for` + накопичення пріоритету | `mapToInt(...).average()` | однакове середнє |
| `for` + `if (isDone())` | `filter(...).count()` | однакова кількість |
| ручна фільтрація | `filter(...)` | еквівалентний набір |
| ручне перетворення об'єктів | `map(...)` | еквівалентний результат |
| ручне групування | `Collectors.groupingBy(...)` | еквівалентна `Map` |
| ручне обчислення статистики | `Collectors.summarizingDouble(...)` | еквівалентна статистика |
| ручне сортування та обмеження | `sorted(...).limit(...)` | еквівалентний top-N |

Еквівалентність основних статистичних показників перевіряється тестом `TaskMetricsEquivalenceTest`.

Окремо перевіряється еквівалентність контрольного звіту.

У тесті результати `TaskMetrics` та `StreamTaskMetrics` передаються до одного `ReportFormatter`, після чого готові рядки звіту порівнюються через `assertEquals`.

Таким чином перевіряється не тільки окреме число, а й збереження зовнішнього формату звіту.

## 13. Порівняння циклової та потокової реалізацій

Порівняння виконується не лише за кількістю рядків коду.

### Циклова реалізація

Переваги:

- проста для покрокового виконання;
- легко зрозуміти порядок команд;
- зручна для базового порівняння результатів.

Недоліки:

- містить змінні-накопичувачі;
- містить ручне керування умовами;
- для складніших операцій потребує додаткової службової логіки;
- описує більше деталей способу виконання.

### Stream API

Переваги:

- декларативний опис операцій;
- добре видно послідовність обробки даних;
- зручно комбінувати `filter`, `map`, `sorted`, `limit`;
- зручно використовувати готові колектори;
- обробка виконується через спільний поліморфний тип `ProjectTask`;
- відсутня необхідність змінювати вхідну колекцію.

Наприклад, Stream API безпосередньо описує необхідний результат: відфільтрувати незавершені задачі, перетворити задачі на назви, згрупувати їх або отримати top-N.

Отже, Stream API підвищує декларативність обробки колекцій та зменшує кількість службової логіки.

## 15. Відповіді на контрольні питання

### 1. Що таке Stream API?

Stream API — це засіб Java для декларативної обробки послідовностей елементів. Він дозволяє описувати операції над колекціями через ланцюжок потокових операцій.

### 2. Чим Stream відрізняється від Collection?

Collection зберігає дані, а Stream описує процес їх обробки.

Одна колекція може використовуватися для створення декількох різних потоків.

### 3. Що таке проміжні операції?

Проміжні операції формують наступний етап потоку та не завершують його обробку.

Приклади: `filter`, `map`, `sorted`.

### 4. Що таке термінальні операції?

Термінальна операція завершує обробку потоку та створює результат або побічний ефект.

Приклади: `collect`, `count`, `sum`, `findFirst`.

### 5. Для чого використовується filter?

`filter` залишає тільки ті елементи, які відповідають заданій умові.

У проєкті він використовується для отримання незавершених задач.

### 6. Для чого використовується map?

`map` перетворює кожен елемент потоку на інше значення.

У проєкті він використовується для перетворення `ProjectTask` у `String`, тобто для отримання назв задач.

### 7. Для чого використовується groupingBy?

`groupingBy` розподіляє елементи за ключем.

У проєкті задачі групуються за відповідальною особою.

### 8. Що таке Collector?

Collector визначає спосіб накопичення елементів потоку в кінцевий результат.

Наприклад, `Collectors.toList()` або `Collectors.groupingBy(...)`.

### 9. Для чого використовується summarizingDouble?

`summarizingDouble` дозволяє отримати основні статистичні характеристики числового поля: кількість, суму, середнє, мінімум та максимум.

### 10. Як реалізується top-N?

Спочатку елементи сортуються за необхідними критеріями, після чого використовується `limit(n)`.

У цій роботі використано складений `Comparator` з основним і вторинним критеріями.

### 11. Навіщо використовувати reversed?

`reversed()` змінює напрямок сортування.

У `topByPriority` він використовується для сортування пріоритетів за спаданням.

### 12. Для чого використовується thenComparing?

`thenComparing` додає вторинний критерій сортування.

Якщо дві задачі мають однаковий пріоритет, вони порівнюються за оцінкою годин.

### 13. Як обробляється порожній список?

Порожній список не повинен спричиняти помилку для звичайних запитів.

Наприклад:

- `filter` повертає порожній список;
- `map` повертає порожній список;
- `groupingBy` повертає порожню мапу;
- `count` повертає `0`;
- `average()` повертає порожній `OptionalDouble`, для якого в реалізації використано `orElse(0.0)`.

### 14. Для чого використовується Optional?

`Optional` дозволяє явно представити можливість відсутності результату.

У проєкті він використовується для пошуку задачі за назвою.

### 15. Чому не потрібно змінювати вхідну колекцію?

Потокова обробка дозволяє створювати нові результати без зміни початкової колекції.

Це зменшує ризик побічних ефектів і спрощує тестування.

### 16. Чому Stream API підходить для поліморфної колекції?

Потік працює через спільний тип `ProjectTask`.

Методи, наприклад `ProjectTask::evaluatePriority`, викликаються поліморфно.

Тому Stream API не потребує перевірки конкретного підтипу.

### 17. Чи можна повторно використати Stream?

Ні. Після виконання термінальної операції конкретний Stream вважається спожитим.

Для нової обробки потрібно створити новий Stream від джерела.

### 18. Яка різниця між map та mapToInt / mapToDouble?

`map` створює звичайний `Stream<T>`, а `mapToInt` та `mapToDouble` створюють спеціалізовані числові потоки.

Числові потоки зручні для операцій `sum`, `average`, `min` та `max`.

### 19. Чому в проєкті залишено циклову реалізацію?

`TaskMetrics` залишено як контрольну реалізацію.

Це дозволяє безпосередньо порівняти результати старого циклового підходу та нового Stream API та переконатися, що рефакторинг не змінив результати програми.

### 20. Як перевіряється правильність рефакторингу?

Правильність перевіряється через:

- автоматичні тести;
- порівняння `TaskMetrics` та `StreamTaskMetrics`;
- порівняння контрольних звітів;
- перевірку порожнього вводу;
- перевірку граничних та негативних випадків;
- запуск `./mvnw clean verify`;
- SpotBugs.
