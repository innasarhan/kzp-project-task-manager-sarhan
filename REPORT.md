# 2. Постановка задачі

Для варіанта 22 предметною областю є «Проєктні задачі».

У попередній лабораторній роботі всі задачі представлялися одним класом ProjectTask.

У лабораторній роботі №3 модель розширено двома спеціалізованими підтипами:

- DevelopmentTask — задача розробки;
- TestingTask — задача тестування.

Також створено enum TaskKind зі значеннями DEVELOPMENT та TESTING.

Основною поліморфною операцією є метод evaluatePriority(). Його реалізація залежить від конкретного типу задачі.

# 3. Класова модель

## 3.1. Базовий тип ProjectTask

ProjectTask є спільним базовим типом для проєктних задач.

Клас містить спільний стан усіх задач:

- title;
- assignee;
- estimateHours;
- priority;
- done.

У ProjectTask централізовано реалізовано спільні інваріанти:

- title не може бути null або порожнім;
- assignee не може бути null або порожнім;
- estimateHours має бути скінченним та не може бути від'ємним;
- priority не може бути від'ємним.

Завдяки цьому правила валідації не дублюються у підтипах.

ProjectTask також містить:

- fromCsv();
- гетери;
- evaluatePriority();
- getKind();
- equals();
- hashCode();
- toString().

Базовий клас залишено конкретним для збереження зворотної сумісності з попередньою лабораторною роботою, оскільки попередні тести безпосередньо створюють об'єкти ProjectTask.

## 3.2. DevelopmentTask

DevelopmentTask представляє задачу розробки.

Клас успадковує спільні поля та правила від ProjectTask і перевизначає метод evaluatePriority().

Правило для задачі розробки:

- якщо estimateHours >= 10.0, до базового пріоритету додається 1;
- якщо оцінка менша за 10 годин, використовується базовий пріоритет.

Наприклад, для priority = 2 та estimateHours = 12.5 результат evaluatePriority() дорівнює 3.

Метод getKind() повертає TaskKind.DEVELOPMENT.

## 3.3. TestingTask

TestingTask представляє задачу тестування.

Клас також успадковує спільний стан та правила від ProjectTask, але має власне правило оцінювання пріоритету.

Для задачі тестування:

- якщо задача виконана, пріоритет не збільшується;
- якщо задача не виконана, до базового пріоритету додається 1.

Наприклад, для priority = 3 та done = false результат evaluatePriority() дорівнює 4.

Метод getKind() повертає TaskKind.TESTING.

Таким чином, DevelopmentTask і TestingTask мають різні реалізації одного поліморфного методу.

# 4. Enum TaskKind

Для представлення типу задачі створено enum TaskKind.

Enum містить два значення:

- DEVELOPMENT;
- TESTING.

Використання enum дозволяє обмежити набір допустимих типів задач, підвищує типобезпечність та робить модель зрозумілішою.

# 5. Поліморфізм

Однією з основних цілей лабораторної роботи було використання поліморфізму.

Об'єкти різних підтипів можуть оброблятися через спільний тип ProjectTask.

Наприклад, колекція List<ProjectTask> може містити одночасно DevelopmentTask та TestingTask.

Для кожного об'єкта можна викликати спільний метод evaluatePriority().

Код не повинен знати конкретний клас об'єкта.

Для DevelopmentTask виконується його реалізація evaluatePriority(), а для TestingTask — його власна реалізація.

У реалізації не використовується if або switch для визначення конкретного підтипу та вибору алгоритму.

Вибір відповідної реалізації виконується механізмом поліморфізму Java.

# 6. Поліморфізм у TaskMetrics

У попередній лабораторній роботі середній пріоритет обчислювався через безпосередній доступ до priority.

У лабораторній роботі №3 TaskMetrics використовує evaluatePriority().

Таким чином, TaskMetrics працює через спільний тип ProjectTask і не знає про конкретні підтипи.

Коли TaskMetrics викликає task.evaluatePriority(), Java автоматично виконує реалізацію відповідного підтипу.

Це дозволяє додавати нові типи задач без необхідності змінювати логіку TaskMetrics.

# 7. Порівняння з попередньою реалізацією

У лабораторній роботі №2 модель складалася переважно з одного класу ProjectTask.

У лабораторній роботі №3 модель розширено:

ProjectTask
├── DevelopmentTask
└── TestingTask

У попередній реалізації пріоритет задачі отримувався безпосередньо через getPriority().

У новій реалізації використовується evaluatePriority(), що дозволяє кожному підтипу застосовувати власне правило.

Основна відмінність полягає в тому, що раніше поведінка була однаковою для всіх задач, а тепер різні типи можуть мати різну поведінку без зміни коду, який працює зі спільним типом.

При цьому існуючий CSV-файл продовжує оброблятися без зміни формату.

Для поточного набору вхідних даних результати метрик залишилися сумісними з попередньою реалізацією.

# 8. Спадкування чи композиція

Для цієї предметної області використано спадкування.

DevelopmentTask є ProjectTask, а TestingTask є ProjectTask.

Обидва підтипи мають спільні поля, інваріанти та правила валідації, але відрізняються поведінкою evaluatePriority().

Тому відношення між класами відповідає моделі is-a.

Композиція могла б бути використана, наприклад, для окремого об'єкта-стратегії, який відповідав би за алгоритм оцінювання пріоритету.

Проте в межах цієї моделі DevelopmentTask і TestingTask є саме різновидами ProjectTask, тому спадкування дозволяє представити спільну частину моделі без дублювання та реалізувати різну поведінку через перевизначення методів.

# 9. equals() та hashCode()

Для ProjectTask реалізовано equals() та hashCode().

При порівнянні враховуються значення полів об'єкта та його конкретний клас.

Тому два однакові об'єкти одного типу вважаються рівними.

Об'єкти різних підтипів не вважаються рівними лише через однакові значення їхніх полів.

Методи equals() і hashCode() реалізовані узгоджено.

Для перевірки використано автоматичні тести.

Зокрема, перевіряється поведінка HashSet: однакові об'єкти не повинні створювати дублікати.

# 21. Відповіді на контрольні питання

## 21.1. Що таке спадкування і для чого воно використовується?

Спадкування — це механізм об'єктно-орієнтованого програмування, за допомогою якого один клас отримує поля та методи іншого класу.

У цьому проєкті DevelopmentTask та TestingTask успадковують ProjectTask.

Спадкування використано для представлення відношення «є різновидом».

Підтипи використовують спільний стан та правила базового класу, але можуть мати власну реалізацію поведінки.

## 21.2. Чому спільні поля винесено в базовий клас?

Спільні поля title, assignee, estimateHours, priority та done є властивостями будь-якої проєктної задачі.

Якби вони були окремо визначені у кожному підтипі, виникло б дублювання коду.

Винесення цих полів у ProjectTask дозволяє:

- мати єдине визначення спільного стану;
- централізувати валідацію;
- уникнути дублювання;
- спростити підтримку коду.

## 21.3. Що таке поліморфізм?

Поліморфізм дозволяє працювати з об'єктами різних класів через спільний тип і викликати метод, реалізація якого залежить від фактичного типу об'єкта.

У роботі таким методом є evaluatePriority().

Код працює з ProjectTask, але фактично може отримати DevelopmentTask або TestingTask.

Під час виклику evaluatePriority() Java виконує перевизначену реалізацію фактичного класу.

## 21.4. Чому поліморфізм дозволяє уникнути if/switch за типом?

Якщо використовувати if або switch для визначення підтипу, код, який обробляє задачі, повинен знати всі конкретні класи.

При додаванні нового підтипу такий код потрібно було б змінювати.

При поліморфізмі кожен підтип сам відповідає за свою поведінку.

Тому код, який працює з ProjectTask, не залежить від конкретної кількості підтипів.

## 21.5. Що таке enum?

enum — це спеціальний тип Java для представлення обмеженої множини наперед визначених значень.

У роботі TaskKind містить DEVELOPMENT та TESTING.

Це дозволяє типобезпечно представляти вид задачі та не використовувати довільні рядки.

## 21.6. Для чого потрібні equals() та hashCode()?

equals() визначає логічну рівність об'єктів.

hashCode() повертає хеш-код об'єкта.

Для рівних через equals() об'єктів hashCode() повинен бути однаковим.

Це особливо важливо для колекцій, які використовують хешування, зокрема HashSet та HashMap.

У роботі правильність equals()/hashCode() перевіряється автоматичними тестами.

## 21.7. Чому не можна реалізувати equals() без hashCode()?

Якщо equals() перевизначено, але hashCode() не узгоджений із ним, колекції на основі хешування можуть працювати неправильно.

Наприклад, HashSet може не розпізнати два логічно однакові об'єкти як дублікати.

Тому equals() та hashCode() повинні реалізовуватися узгоджено.

## 21.8. Що таке різнорідна колекція?

Різнорідна колекція — це колекція, яка містить об'єкти різних конкретних класів, але всі вони мають спільний базовий тип.

У роботі List<ProjectTask> може містити DevelopmentTask та TestingTask.

Це демонструє практичне використання поліморфізму.

## 21.9. Чому використано спадкування, а не композицію?

DevelopmentTask та TestingTask є різновидами ProjectTask.

Вони мають спільний стан та інваріанти, але різну реалізацію evaluatePriority().

Тому спадкування відповідає відношенню is-a.

Композиція була б доцільнішою для окремої незалежної поведінки, яку потрібно динамічно підміняти, наприклад для стратегії оцінювання.

У цій моделі спадкування дозволяє без дублювання представити спільну частину доменної моделі та різну поведінку підтипів.

## 21.10. Як забезпечено зворотну сумісність?

Збережено:

- попередній CSV-формат;
- існуючі правила валідації;
- попередні тести;
- зовнішній формат звіту;
- можливість створення звичайного ProjectTask.

Нова функціональність додана поверх попередньої моделі, а не шляхом повного переписування програми.

# 22. Академічна доброчесність

Під час виконання лабораторної роботи використовувалися сучасні інструменти підтримки розробки програмного забезпечення, зокрема GitHub Copilot та ChatGPT.

Основним інструментом штучного інтелекту під час безпосередньої роботи з програмним кодом був GitHub Copilot.

Використання AI-інструментів не замінювало самостійну роботу над проєктом. Запропонований код перевірявся, адаптувався до структури конкретного проєкту та тестувався перед включенням до фінальної версії.

## 22.1. Використання GitHub Copilot

GitHub Copilot використовувався переважно як інструмент програмістської підтримки.

Зокрема, Copilot допомагав:

- формувати заготовки Java-класів;
- доповнювати методи;
- створювати типові конструкції Java;
- пропонувати реалізації equals() та hashCode();
- створювати та доповнювати Javadoc;
- пропонувати варіанти автоматичних тестів;
- знаходити можливі причини помилок компіляції;
- пропонувати варіанти рефакторингу;
- працювати з Maven-конфігурацією;
- формувати ідеї для позитивних, граничних та негативних тестів;
- допомагати аналізувати структуру класів;
- допомагати перевіряти можливі варіанти реалізації методів.

Copilot був особливо корисним для створення типового та повторюваного коду.

Водночас предметні рішення не передавалися Copilot без перевірки.

Наприклад, логіка DevelopmentTask та TestingTask була визначена відповідно до вимог лабораторної роботи.

Так само окремо перевірялося, що поліморфна реалізація використовує перевизначення evaluatePriority(), а не if або switch за типом.

## 22.2. Перевірка коду, запропонованого Copilot

Код, запропонований GitHub Copilot, не приймався автоматично.

Перед включенням змін до проєкту виконувалися:

1. перегляд запропонованого коду;
2. перевірка відповідності вимогам лабораторної роботи;
3. перевірка сумісності з існуючою моделлю;
4. перевірка збереження CSV-формату;
5. запуск автоматичних тестів;
6. запуск Maven verify;
7. запуск SpotBugs;
8. перегляд змін через Git diff;
9. перевірка результату CI.

Особлива увага приділялася equals()/hashCode(), поліморфізму, спадкуванню, валідації та зворотній сумісності.

Таким чином, GitHub Copilot використовувався як допоміжний інструмент, а не як джерело готової роботи, яка приймається без перевірки.
