## 3. Стан «до / після»

### 3.1. До виконання лабораторної роботи

Для роботи з даними можна використовувати звичайні колекції та предметно-орієнтовану логіку.

Якщо операції експорту й імпорту реалізовані окремо для конкретного класу, додавання або зміна полів може вимагати редагування відповідного коду. Такий підхід ускладнює повторне використання реалізації для інших типів даних.

### 3.2. Після виконання лабораторної роботи

Створено узагальнений клас `Repository<T>`, який зберігає об'єкти заданого типу та підтримує пошук за переданою умовою.

Для CSV-експорту використовується анотація `@CsvColumn`. Вона визначає, які поля потрібно включати у файл і які назви стовпців використовувати.

Клас `CsvExporter` отримує метадані полів за допомогою рефлексії та формує CSV. Клас `CsvImporter` читає файл, перевіряє його структуру та відновлює об'єкти відповідного класу.

Для роботи з файловою системою використовуються `Path` і `Files`, а кодування UTF-8 задається явно.

Для повідомлення про помилки формату створено `CsvFormatException`, який дає змогу передавати контекст помилки та зберігати початкову причину.

Таким чином, реалізація стала більш універсальною, а експорт та імпорт можна перевіряти автоматичними тестами.

## 4. Контракт даних і доменна модель

### 4.1. Клас ProjectTaskRecord

Для CSV-операцій використовується клас `ProjectTaskRecord`, який описує окрему проєктну задачу.

Відповідно до варіанта 22, клас містить такі поля:

| Java-поле | Тип | Назва CSV-стовпця | Призначення |
|---|---|---|---|
| `name` | `String` | `назва` | Назва задачі |
| `assignee` | `String` | `виконавець` | Відповідальна особа |
| `estimatedHours` | `double` | `години` | Оцінка задачі в годинах |
| `status` | `TaskStatus` | `статус` | Поточний стан задачі |
| `priority` | `TaskPriority` | `пріоритет` | Пріоритет задачі |

Текстові поля представлені типом `String`, оцінка часу — типом `double`, а стан і пріоритет — enum.

Конструктор перевіряє допустимість значень: текстові поля не повинні бути порожніми, оцінка годин має бути скінченною та невід'ємною, а значення enum не повинні бути `null`.

### 4.2. Перелічувані типи

Для стану задачі використовується `TaskStatus`:

- `TODO`;
- `IN_PROGRESS`;
- `DONE`.

Для пріоритету використовується `TaskPriority`:

- `LOW`;
- `MEDIUM`;
- `HIGH`.

У CSV значення enum записуються як їхні імена. Під час імпорту вони перетворюються назад на відповідні значення enum. Невідоме значення вважається некоректними вхідними даними.

### 4.3. Анотація CsvColumn

Анотація `@CsvColumn` визначає назву стовпця для поля, яке бере участь у CSV-операціях.

Анотація має зберігатися під час виконання програми, щоб експортер та імпортер могли отримувати її через рефлексію. Для цього використовується політика `RetentionPolicy.RUNTIME`. Обмеження `ElementType.FIELD` визначає, що анотацію можна застосовувати до полів класу.

Назви CSV-стовпців беруться саме з `@CsvColumn`, а не формуються автоматично з Java-імен полів.

### 4.4. Порядок стовпців

Порядок стовпців визначається сортуванням Java-імен полів за алфавітом. Це забезпечує детермінований формат незалежно від порядку, у якому рефлексія повертає поля.

Для `ProjectTaskRecord` порядок буде таким:

1. `assignee`;
2. `estimatedHours`;
3. `name`;
4. `priority`;
5. `status`.

Відповідні назви стовпців CSV:

```csv
виконавець,години,назва,пріоритет,статус
```

Такий самий порядок використовується для значень кожного запису.

### 4.5. Ключ запису

Логічний ідентифікатор запису визначається комбінацією полів `name` та `assignee`.

Метод `hasSameIdentity(ProjectTaskRecord other)` перевіряє, чи збігаються назва задачі та відповідальна особа.

При цьому `equals()` і `hashCode()` враховують усі п'ять полів. Тому два записи можуть мати однаковий логічний ідентифікатор, але бути різними об'єктами за повним значенням полів.

Таке розділення дає змогу окремо перевіряти ідентичність задачі та повну рівність записів.

## 5. Параметризоване сховище Repository<T>

Клас `Repository<T>` реалізує узагальнене сховище об'єктів заданого типу.

Параметр типу `T` дає змогу повторно використовувати одну реалізацію для різних класів, зберігаючи перевірку типів під час компіляції.

Внутрішньо сховище використовує колекцію `List<T>`.

### 5.1. Додавання елементів

Метод `add(T item)` додає елемент до сховища.

Перед додаванням перевіряється, що передане значення не є `null`. Для цього використовується `Objects.requireNonNull`.

Це запобігає потраплянню `null` до внутрішньої колекції.

### 5.2. Отримання знімка

Метод `snapshot()` повертає незмінний знімок поточного вмісту сховища.

Для створення знімка використовується `List.copyOf(items)`. Отриманий список не дозволяє зовнішньому коду додавати чи видаляти елементи через повернене значення.

Це захищає внутрішню колекцію від безпосередньої модифікації через знімок.

### 5.3. Пошук за умовою

Метод `search(Predicate<T> predicate)` виконує пошук елементів за переданою умовою.

`Predicate<T>` представляє функцію, яка перевіряє елемент і повертає логічне значення. Для фільтрації використовується Stream API.

Наприклад, можна знайти задачі з високим пріоритетом:

```java
repository.search(
    item -> item.getPriority() == TaskPriority.HIGH
);
```

Такий підхід дає змогу задавати різні критерії пошуку без створення окремого методу для кожного з них.

Метод також перевіряє, що переданий предикат не є `null`.

### 5.4. Додаткові операції

Метод `size()` повертає кількість елементів у сховищі.

Метод `isEmpty()` перевіряє, чи містить сховище хоча б один елемент.

Ці операції спрощують контроль стану сховища та його тестування.

### 5.5. Переваги узагальнення

Основні переваги `Repository<T>`:

- повторне використання коду;
- перевірка типів під час компіляції;
- зменшення кількості приведень типів;
- відокремлення зберігання від предметної логіки;
- можливість тестування сховища незалежно від CSV-операцій;
- підтримка різних умов пошуку через `Predicate<T>`.

## 6. Анотації та рефлексія

Для універсального CSV-експорту використовується анотація `CsvColumn` разом із механізмом рефлексії Java.

### 6.1. Призначення анотації

Анотація `CsvColumn` містить метадані, які використовуються для формування заголовків CSV.

Сама анотація не виконує запис файлу. Вона лише описує поля, які повинні брати участь у CSV-операціях.

### 6.2. Використання рефлексії

Рефлексія дає змогу отримувати інформацію про поля класу під час виконання програми.

Завдяки цьому `CsvExporter` може знаходити поля з анотацією, отримувати їхні значення та формувати рядки CSV без окремо написаної логіки для кожного поля.

Поля без відповідної анотації не повинні автоматично ставати стовпцями CSV.

### 6.3. Доступ до полів

Під час роботи з рефлексією потрібно враховувати модифікатори доступу. Якщо поле недоступне для рефлексивної операції, проблема має оброблятися явно, а не приховуватися.

Це важливо для надійності універсального механізму експорту.

### 6.4. Детермінований порядок

Перед формуванням заголовка та значень поля сортуються за Java-іменами.

Детермінований порядок забезпечує:

- стабільний формат CSV;
- повторювані результати експорту;
- передбачувані автоматичні тести;
- узгодженість заголовків і значень під час імпорту.

## 7. CSV-експорт та екранування значень

Клас `CsvExporter` відповідає за перетворення об'єктів на CSV-представлення та запис результату у файл.

Експортер використовує метадані анотації `CsvColumn`, отримує значення полів через рефлексію та формує стовпці в детермінованому порядку.

### 7.1. Формування заголовка

Заголовок CSV формується з назв, заданих в анотаціях.

Для `ProjectTaskRecord` очікується такий заголовок:

```csv
виконавець,години,назва,пріоритет,статус
```

Порядок заголовків відповідає сортуванню Java-імен полів, а не порядку оголошення полів у класі.

### 7.2. Екранування спеціальних символів

Текстове поле може містити кому, подвійну лапку або перенесення рядка.

Якщо поле містить один із цих символів, воно береться в подвійні лапки. Подвійна лапка всередині поля подвоюється.

Наприклад, значення назви задачі:

```text
API, v2
```

має бути представлене в CSV як:

```csv
"API, v2"
```

Значення:

```text
Fix "login"
```

представляється як:

```csv
"Fix ""login"""
```

Перенесення рядка всередині поля також має залишатися частиною значення, а не розділяти один запис на два логічні записи.

Тому один CSV-запис може займати кілька фізичних рядків текстового файлу.

### 7.3. Приклад CSV

Нижче наведено умовний приклад CSV для проєктних задач:

```csv
виконавець,години,назва,пріоритет,статус
Olena,4.5,"API, v2",HIGH,IN_PROGRESS
Ivan,2.0,"Fix ""login""",MEDIUM,TODO
Oksana,1.5,"First line
Second line",LOW,DONE
Andrii,6.0,Database migration,HIGH,IN_PROGRESS
Maria,2.5,Documentation,MEDIUM,TODO
```

Цей приклад ілюструє порядок стовпців і принципи екранування. Реальне форматування визначається результатом роботи `CsvExporter`.

### 7.4. Запис файлу

Для роботи з файловою системою використовуються `Path` і `Files`.

Кодування UTF-8 задається явно, щоб українські літери та інші текстові символи коректно записувалися й читалися на різних операційних системах.

### 7.5. Порожній список

Окремо перевіряється експорт порожнього списку.

У цьому випадку експортер створює порожній файл. Після імпорту такого файлу імпортер повертає порожній список.

Ця поведінка підтверджена автоматичним тестом `exportingEmptyListCreatesEmptyFileAndImportsEmptyList`.

## 8. CSV-імпорт та обробка помилок

Клас `CsvImporter` відповідає за читання CSV-файлу, перевірку його структури, перетворення значень і відновлення об'єктів.

### 8.1. Перевірка вхідних даних

Під час імпорту перевіряються:

- структура CSV;
- правильна кількість полів;
- коректність лапок;
- можливість перетворення числових значень;
- допустимість значень enum;
- можливість прочитати файл.

### 8.2. Числові значення

Поле `estimatedHours` має тип `double`.

Якщо значення неможливо перетворити на число, імпорт завершується помилкою формату. Некоректне значення не повинно призводити до створення некоректного об'єкта.

Також доменна модель перевіряє, що кількість годин є скінченною та невід'ємною.

### 8.3. Перелічувані типи

Поля `status` і `priority` перетворюються на значення `TaskStatus` та `TaskPriority`.

Якщо CSV містить невідоме значення, наприклад `URGENT` для пріоритету, імпортер повідомляє про помилку.

### 8.4. Власний виняток CsvFormatException

Для помилок CSV використовується власний виняток `CsvFormatException`.

Він дає змогу повідомити про проблему у зрозумілому форматі та зберегти початкову причину через механізм `cause`.

Збереження початкової причини допомагає під час діагностики. Наприклад, помилка CSV може бути пов'язана з некоректним числовим значенням або проблемою файлового введення-виведення.

Окремий тест перевіряє, що у випадку відсутнього файлу початковий виняток `IOException` зберігається як причина `CsvFormatException`.

### 8.5. Таблиця помилок

| Ситуація | Очікувана поведінка |
|---|---|
| Неправильна кількість полів | `CsvFormatException` |
| Некоректне числове значення | Помилка перетворення |
| Невідоме значення enum | Помилка формату CSV |
| Незакрита подвійна лапка | Помилка структури CSV |
| Файл недоступний | Помилка збережена як причина винятку |
| Порожній файл | Повернення порожнього списку |
| Порожній набір для експорту | Створення порожнього CSV-файлу |

Помилки не повинні поглинатися порожнім блоком `catch`, оскільки це приховує причину невдалого виконання та ускладнює діагностику.

## 9. Перевірка round-trip і відновлення записів

Для перевірки узгодженості експорту та імпорту використовується підхід round-trip.

Round-trip означає послідовність:

1. створити початкові об'єкти;
2. експортувати їх у CSV;
3. прочитати CSV;
4. відновити об'єкти через імпортер;
5. порівняти відновлені об'єкти з початковими.

### 9.1. Набір тестових записів

У тесті `csvExportAndImportPreserveRecords()` створюється п'ять записів:

| Назва задачі | Виконавець | Години | Особливість |
|---|---|---:|---|
| `API, v2` | Olena | 4.5 | Кома в назві |
| `Fix "login"` | Ivan | 2.0 | Подвійні лапки в назві |
| `First line` з другим рядком `Second line` | Oksana | 1.5 | Перенесення рядка |
| `Database migration` | Andrii | 6.0 | Звичайне текстове значення |
| `Documentation` | Maria | 2.5 | Звичайне текстове значення |

Для кожного запису також задаються стан `TaskStatus` і пріоритет `TaskPriority`.

Таким чином, тест перевіряє як звичайні дані, так і спеціальні символи в текстових полях.

### 9.2. Порівняння результатів

Після експорту виконується імпорт файлу через `CsvImporter`.

Потім використовується перевірка:

```java
assertEquals(original, imported);
```

Вона підтверджує, що відновлений список відповідає початковому списку за визначеною рівністю `ProjectTaskRecord`.

Оскільки `equals()` і `hashCode()` враховують усі п'ять полів, порівняння перевіряє назву, виконавця, оцінку годин, стан і пріоритет.

Логічна ідентичність за комбінацією `name + assignee` додатково перевіряється методом `hasSameIdentity()` в окремому тесті.

### 9.3. Межі перевірки

Round-trip тест підтверджує узгодженість експорту й імпорту для перевірених даних.

Він не замінює окремих тестів для неправильного формату CSV, помилок перетворення, недоступних файлів та порожнього набору даних.

## 13. Порівняння предметного та універсального підходів

### 13.1. Предметний підхід

Предметний підхід передбачає, що код експорту й імпорту безпосередньо знає структуру конкретного класу.

**Переваги:**

- простота для невеликої кількості полів;
- зрозумілий порядок значень;
- можливість явно задавати перетворення кожного поля.

**Недоліки:**

- необхідність змінювати код після додавання полів;
- складніше повторне використання для інших класів;
- ризик дублювання логіки;
- тісний зв'язок предметної моделі з форматом CSV.

### 13.2. Універсальний експортер

Універсальний експортер використовує анотації та рефлексію для отримання даних із класу.

**Переваги:**

- поля визначаються через метадані `@CsvColumn`;
- менша залежність експорту від конкретного предметного класу;
- відсутність необхідності вручну перелічувати кожне поле в кожній операції;
- детермінований порядок стовпців;
- можливість повторного використання механізму.

**Недоліки:**

- рефлексія може ускладнювати налагодження;
- потрібно враховувати доступ до полів;
- необхідно обробляти помилки перетворення й структури CSV;
- потрібно підтримувати узгодженість між правилами експорту та імпорту.

### 13.3. Висновок порівняння

Універсальний підхід зменшує дублювання коду та полегшує повторне використання механізму CSV. Водночас він потребує чіткого контракту анотацій, детермінованого порядку полів, правильного екранування та контрольованої обробки помилок.

## 15. Відповіді на контрольні питання

### 1. Яку проблему розв'язує параметр типу в Repository<T>?

Параметр типу `T` дає змогу створити сховище, яке працює з різними типами об'єктів без дублювання реалізації. Він забезпечує перевірку типів під час компіляції та зменшує потребу в приведеннях типів.

### 2. Чим параметризований клас відрізняється від raw type?

Параметризований клас використовує конкретний аргумент типу, наприклад `Repository<ProjectTaskRecord>`. Raw type — це використання узагальненого класу без аргументу типу, наприклад `Repository`. Raw type послаблює перевірку типів і може спричиняти попередження компілятора.

### 3. Для чого використовується Predicate<T> у методі пошуку?

`Predicate<T>` представляє умову, яка приймає об'єкт типу `T` і повертає `true` або `false`. Це дає змогу передавати різні критерії пошуку без створення окремого методу для кожного критерію.

### 4. Чому snapshot() має повертати незмінний знімок?

Незмінний знімок не дозволяє зовнішньому коду змінювати внутрішню колекцію через отримане посилання. У цій реалізації `snapshot()` використовує `List.copyOf(items)`, що захищає структуру внутрішньої колекції від зовнішньої модифікації через повернений список.

### 5. Що таке checked exception і коли він доречний?

Checked exception — це виняток, який компілятор вимагає обробити через `catch` або оголосити в `throws`. Він доречний для операцій, які можуть завершитися очікуваною помилкою, наприклад файлового введення-виведення. Власний виняток `CsvFormatException` у проєкті використовується для представлення помилок CSV.

### 6. Для чого зберігати cause власного винятку?

Початкова причина допомагає визначити джерело помилки. Наприклад, `CsvFormatException` може містити причину у вигляді `IOException`. Збереження `cause` допомагає під час діагностики й не втрачає інформацію про початкову помилку.

### 7. Чим Path і Files кращі за складання шляху рядком?

`Path` представляє шлях до файлового об'єкта, а `Files` надає готові операції для читання, запису та перевірки файлів. Ці API спрощують файлові операції та допомагають уникнути ручного складання шляхів.

### 8. Чому кодування потрібно задавати і під час запису, і під час читання?

Без явного кодування результат може залежати від системних налаштувань. Якщо файл записано в UTF-8, його потрібно читати в UTF-8, щоб українські літери та інші символи відновлювалися правильно.

### 9. Що роблять @Retention(RUNTIME) і @Target(FIELD)?

`@Retention(RUNTIME)` означає, що анотація доступна під час виконання програми, зокрема через рефлексію. `@Target(FIELD)` обмежує застосування анотації полями класу.

### 10. Чому анотація не виконує експорт сама?

Анотація є метаданими, а не алгоритмом. Вона описує поля, які потрібно експортувати. Саме `CsvExporter` читає ці метадані, отримує значення полів і формує CSV-файл.

### 11. Чим getDeclaredFields() відрізняється від getFields()?

`getDeclaredFields()` повертає поля, оголошені безпосередньо в класі, зокрема непублічні, але не включає успадковані поля. `getFields()` повертає доступні публічні поля класу та його суперкласів.

### 12. Навіщо перевіряти trySetAccessible()?

`trySetAccessible()` дає змогу перевірити, чи вдалося відкрити доступ до поля або іншого члена для рефлексивної операції. Якщо доступ неможливо отримати, програму можна змусити обробити проблему явно, а не несподівано завершувати операцію.

### 13. Чому порядок полів для CSV потрібно зробити детермінованим?

Порядок полів, отриманих через рефлексію, не слід використовувати як неявну гарантію формату. Детерміноване сортування забезпечує повторювані файли, стабільні тести та правильне зіставлення стовпців під час імпорту.

### 14. Чому split(",") не підходить для загального CSV?

Кома може бути роздільником стовпців, але також може входити до значення в лапках. Простий `split(",")` не враховує лапки, екранування та перенесення рядків, тому може неправильно розділити запис.

### 15. Як екрануються кома, лапка й перенесення рядка в CSV?

Поле, що містить кому, подвійну лапку або перенесення рядка, береться в подвійні лапки. Подвійна лапка всередині такого поля подвоюється. Наприклад, текст `новий "модуль"` записується як `"новий ""модуль"""`.

### 16. Чому порожній список потребує окремого параметра Class<T>?

Коли список порожній, неможливо визначити тип об'єкта через перший елемент. `Class<T>` дає змогу передати інформацію про тип явно. Це корисно, якщо експортер повинен отримати метадані класу для формування заголовка навіть без рядків даних. Необхідність такого параметра залежить від API конкретного експортера.

### 17. Чим універсальний експортер відрізняється від предметного fromCsv?

Універсальний експортер використовує загальні правила, анотації та рефлексію, щоб перетворювати об'єкти на CSV без жорстко заданого переліку полів конкретного класу. Предметний `fromCsv` зазвичай знає структуру певного класу та вручну перетворює стовпці на його поля.

### 18. Які рівні помилок розрізняє програма?

У програмі необхідно розрізняти помилки файлового введення-виведення, помилки структури CSV, помилки перетворення типів і помилки допустимості значень. `CsvFormatException` забезпечує єдиний тип винятку для помилок CSV, водночас дозволяючи зберігати початкову причину.

### 19. Що доводить тест round-trip?

Round-trip тест перевіряє узгодженість експорту й імпорту. Якщо після послідовності «об'єкти → CSV → об'єкти» відновлені значення відповідають початковим, це підтверджує правильність роботи з полями, порядком стовпців, екрануванням і перетворенням типів для перевірених випадків.

### 20. Чому виняток не можна поглинати порожнім catch?

Порожній `catch` приховує помилку й не дозволяє викликачеві зрозуміти, що операція завершилася невдало. Це може призвести до втрати інформації або некоректного результату без пояснення. Помилку потрібно обробити, передати далі або обгорнути у виняток із збереженням початкової причини.
