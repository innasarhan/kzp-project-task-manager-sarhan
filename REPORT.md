## 3. Стан «до / після»: параметризоване сховище та CSV

У попередніх реалізаціях проєкту дані оброблялися відповідно до потреб предметної області. У лабораторній роботі №5 додано узагальнений механізм зберігання та універсальну серіалізацію даних у CSV.

### До

Для роботи з даними можна було використовувати конкретні колекції та предметно-орієнтовану логіку.

CSV-обробка, реалізована окремо для певного типу даних, потребує додаткових змін, якщо змінюється модель або додаються нові поля.

### Після

Створено узагальнений клас `Repository<T>`, який дозволяє працювати з елементами заданого типу без прив'язки до конкретного класу задач.

Для CSV-експорту використовується анотація `@CsvColumn`. Вона визначає, які поля потрібно включити у файл і якими заголовками їх позначити.

Клас `CsvExporter` отримує метадані полів через рефлексію, а `CsvImporter` відповідає за читання CSV і перетворення значень на об'єкти.

Для роботи з файлами використовуються `Path`, `Files` та явне кодування UTF-8.

Окремо реалізовано власний виняток `CsvFormatException`, який дозволяє повідомити про помилку формату та зберегти початкову причину.

## 4. Контракт даних та доменна модель

У лабораторній роботі збережено предметну область «Проєктні задачі».

Для CSV-операцій використовується клас `ProjectTaskRecord`, який містить дані про окрему задачу.

### Основні поля ProjectTaskRecord

- `name` — назва задачі;
- `assignee` — відповідальна особа;
- `estimatedHours` — оцінка задачі в годинах;
- `status` — поточний стан задачі;
- `priority` — пріоритет задачі.

Для представлення стану використовується enum `TaskStatus` зі значеннями:

- `TODO`;
- `IN_PROGRESS`;
- `DONE`.

Для представлення пріоритету використовується enum `TaskPriority` зі значеннями:

- `LOW`;
- `MEDIUM`;
- `HIGH`.

### Анотація CsvColumn

Анотація `CsvColumn` використовується для позначення полів, які повинні потрапляти до CSV-файлу.

Для доступу до анотацій під час виконання програми потрібна політика зберігання `RetentionPolicy.RUNTIME`. Обмеження `ElementType.FIELD` визначає, що анотацію можна застосовувати до полів класу.

### Контракт CSV

Порядок стовпців визначається детерміновано, щоб результати експорту не залежали від порядку повернення полів рефлексією.

Для реалізації проєкту використовується заголовок:

```csv
виконавець,години,назва,пріоритет,статус
```

Значення enum записуються відповідно до їхніх імен, наприклад `HIGH` або `IN_PROGRESS`.

Формат CSV має враховувати коми, подвійні лапки та перенесення рядків усередині значень.

## 5. Параметризоване сховище Repository<T>

Клас `Repository<T>` реалізує узагальнене сховище для об'єктів заданого типу.

Параметр типу `T` дозволяє повторно використовувати одну реалізацію для різних класів, зберігаючи перевірку типів під час компіляції.

### 5.1. Додавання елементів

Сховище підтримує додавання елементів типу `T`.

Узагальнення дозволяє уникнути необґрунтованого використання типу `Object` та ручних приведень типів під час роботи з елементами.

### 5.2. Отримання знімка

Метод отримання знімка повертає представлення поточного вмісту сховища, яке не дає зовнішньому коду безпосередньо змінювати внутрішню колекцію.

Це допомагає захистити внутрішній стан сховища від випадкової модифікації через повернене значення.

### 5.3. Пошук за умовою

Для пошуку використовується `Predicate`, який описує умову, що перевіряється для кожного елемента.

Такий підхід дозволяє передавати різні умови пошуку без необхідності створювати окремий метод для кожного критерію.

Наприклад, можна шукати задачі за назвою, відповідальною особою або станом.

### 5.4. Переваги узагальнення

Основні переваги `Repository<T>`:

- повторне використання коду;
- перевірка типів на етапі компіляції;
- зменшення кількості приведень типів;
- відокремлення зберігання від предметної логіки;
- можливість тестування сховища незалежно від CSV-операцій.

## 6. Анотації та рефлексія

Для універсального експорту використовується анотація `CsvColumn` разом із механізмом рефлексії Java.

### Анотація

`CsvColumn` містить метадані, які використовуються для формування заголовків CSV.

Анотація сама не виконує запис файлу. Вона лише описує поля, які повинні бути оброблені експортером.

### Рефлексія

Рефлексія дозволяє отримати інформацію про поля класу під час виконання програми.

Завдяки цьому `CsvExporter` може знаходити поля з анотацією та отримувати їхні значення без написання окремої логіки для кожного поля.

Поля, які не мають відповідної анотації, не повинні автоматично ставати стовпцями CSV.

### Доступ до полів

Під час роботи з рефлексією необхідно враховувати модифікатори доступу. Якщо поле недоступне для читання, експортер повинен коректно обробити цю ситуацію, а не мовчки ігнорувати проблему.

### Детермінований порядок

Поля сортуються за визначеним правилом перед формуванням заголовка та рядків даних.

Детермінований порядок потрібен для:

- стабільних результатів експорту;
- повторюваних тестів;
- передбачуваного формату файлу;
- коректного зіставлення заголовків і значень під час імпорту.

## 7. CSV-експорт та екранування значень

Клас `CsvExporter` відповідає за перетворення об'єктів на CSV-представлення та запис результату у файл.

Експортер використовує метадані анотації `CsvColumn`, а не жорстко заданий список полів конкретного предметного класу.

### Формування заголовка

Заголовок CSV формується з назв, заданих в анотаціях. Порядок стовпців є детермінованим.

Приклад заголовка:

```csv
виконавець,години,назва,пріоритет,статус
```

### Екранування

Значення CSV можуть містити спеціальні символи.

Якщо поле містить кому, подвійні лапки або перенесення рядка, його потрібно записати в подвійних лапках. Подвійна лапка всередині такого поля подвоюється.

Приклад значення з комою:

```csv
Олена,4.5,"Реалізувати модуль, частина 1",HIGH,TODO
```

Приклад значення з подвійними лапками:

```csv
Олена,4.5,"Перевірити ""новий"" модуль",HIGH,TODO
```

Якщо поле містить перенесення рядка, воно залишається всередині поля в подвійних лапках. Тому один CSV-запис не обов'язково відповідає одному фізичному рядку текстового файлу.

### Запис файлу

Для роботи з файловою системою використовуються `Path` і `Files`. Кодування UTF-8 задається явно, щоб текстові дані з українськими літерами коректно записувалися на різних операційних системах.

Якщо список порожній, експортер має коректно обробити цей випадок і сформувати передбачуваний результат відповідно до реалізованого контракту.

## 8. CSV-імпорт та обробка помилок

Клас `CsvImporter` відповідає за читання CSV-файлу, перевірку його структури та відновлення об'єктів.

### Перевірка вхідних даних

Під час імпорту перевіряються:

- відповідність заголовка очікуваному формату;
- правильна кількість полів у записі;
- коректність CSV-лапок;
- можливість перетворення числових значень;
- допустимість значень enum;
- доступність файлу для читання.

### Числові значення

Якщо значення `estimatedHours` не можна перетворити на число, імпорт повинен повідомити про помилку формату, а не повертати некоректний об'єкт.

### Enum

Значення полів `status` і `priority` повинні відповідати допустимим значенням `TaskStatus` та `TaskPriority`.

Невідоме значення enum розглядається як помилка вхідних даних.

### Власний виняток

Для помилок CSV використовується `CsvFormatException`.

Виняток дозволяє надати зрозумілий контекст помилки та зберегти початкову причину через механізм `cause`.

Збереження причини важливе для діагностики: наприклад, початковим винятком може бути помилка перетворення числа або помилка введення-виведення.

### Таблиця основних помилок

| Ситуація | Очікувана поведінка |
|---|---|
| Неправильна кількість полів | Повідомлення про помилку формату CSV |
| Некоректне числове значення | Помилка перетворення збережена як причина |
| Невідоме значення enum | Повідомлення про некоректне значення |
| Незакрита подвійна лапка | Повідомлення про некоректний CSV |
| Файл недоступний | Повідомлення про помилку введення-виведення |
| Порожній файл | Коректна обробка відповідно до контракту імпортера |

Помилки не повинні поглинатися порожнім блоком `catch`, оскільки це ускладнює пошук проблем і може приховати пошкоджені дані.

## 9. Еквівалентність «CSV → об'єкти → CSV»

Для перевірки коректності CSV-операцій використовується підхід round-trip.

Round-trip означає послідовність:

1. створити початкові об'єкти;
2. експортувати їх у CSV;
3. прочитати CSV;
4. відновити об'єкти через імпортер;
5. порівняти відновлені дані з початковими.

### Перевірка

Під час перевірки потрібно враховувати не тільки прості текстові значення, а й спеціальні випадки:

- коми всередині поля;
- подвійні лапки;
- перенесення рядків;
- числові значення;
- enum;
- порожній набір даних.

### Очікуваний результат

Після експорту та імпорту відновлені об'єкти повинні зберігати значення полів, представлених у CSV.

Якщо тест перевіряє об'єктну рівність, результат залежить від визначення `equals` у відповідній моделі. Якщо рівність об'єктів не використовується, можна порівнювати окремі поля.

Round-trip тест підтверджує, що експортер та імпортер узгоджено трактують порядок стовпців, екранування і перетворення типів.

Він не замінює окремих тестів для некоректних даних, файлових помилок і граничних випадків.

## 13. Порівняння предметного та універсального підходів

Порівняння виконується між підходом, за якого обробка CSV залежить від конкретного класу, та універсальним експортером, який використовує анотації й рефлексію.

### Предметний підхід

Переваги:

- простий для невеликої кількості полів;
- легко явно визначити порядок значень;
- логіка може бути зрозумілою для одного конкретного класу.

Недоліки:

- потрібно змінювати код після додавання полів;
- складніше повторно використовувати реалізацію для інших класів;
- логіка серіалізації може дублюватися;
- предметна модель тісно пов'язується з форматом CSV.

### Універсальний експортер

Переваги:

- використовує метадані анотацій;
- зменшує залежність експорту від конкретної предметної моделі;
- дозволяє визначати поля для експорту без окремого ручного переліку в кожному виклику;
- підтримує детермінований порядок стовпців;
- полегшує повторне використання логіки.

Недоліки:

- рефлексія складніша для налагодження;
- необхідно враховувати доступ до полів;
- потрібно явно обробляти помилки доступу й перетворення;
- коректність залежить від правил формування та інтерпретації CSV.

Отже, універсальний підхід зменшує дублювання логіки експорту, але потребує чітких правил анотацій, порядку полів, екранування та обробки помилок.

## 15. Відповіді на контрольні питання

### 1. Яку проблему розв'язує параметр типу в Repository<T>?

Параметр типу `T` дозволяє створити сховище, яке працює з різними типами об'єктів, не дублюючи реалізацію. Він також дає змогу перевіряти типи під час компіляції та зменшує потребу в приведеннях типів.

### 2. Чим параметризований клас відрізняється від raw type?

Параметризований клас використовує конкретний аргумент типу, наприклад `Repository<ProjectTaskRecord>`. Raw type — це використання узагальненого класу без аргументу типу, наприклад `Repository`. Raw type послаблює перевірку типів і може спричиняти попередження компілятора.

### 3. Навіщо Predicate<? super T> у методі пошуку?

`Predicate` представляє умову, яка повертає `true` або `false`. Варіант `? super T` дозволяє передавати предикат для самого типу `T` або його суперкласу. Це робить API гнучкішим завдяки контраваріантності споживача значень.

### 4. Чому all() має повертати незмінний знімок?

Незмінний знімок не дозволяє зовнішньому коду змінювати внутрішню колекцію сховища через отримане посилання. Це захищає стан сховища та робить поведінку його методів передбачуванішою. Якщо в реалізації метод називається `snapshot()`, він виконує відповідну роль отримання знімка.

### 5. Що таке checked exception і коли він доречний у цій роботі?

Checked exception — це виняток, який компілятор вимагає обробити через `catch` або оголосити в `throws`. Він доречний, коли операція може очікувано завершитися помилкою, яку викликач має врахувати, наприклад під час читання чи запису файлів.

### 6. Для чого зберігати cause власного винятку?

Початкова причина допомагає визначити джерело помилки. Наприклад, `CsvFormatException` може містити інформацію про помилку перетворення числа або файлову помилку. Якщо зберігати тільки текст повідомлення, частина діагностичної інформації втрачається.

### 7. Чим Path і Files кращі за складання шляху рядком?

`Path` представляє шлях до файлового об'єкта, а `Files` надає готові операції для читання, запису та перевірки файлів. Ці API краще враховують відмінності файлових систем і зменшують потребу вручну складати шляхи та реалізовувати файлові операції.

### 8. Чому кодування потрібно задавати і під час запису, і під час читання?

Без явного кодування результат може залежати від системних налаштувань. Якщо файл записаний в UTF-8, його потрібно читати в UTF-8, щоб українські літери та інші символи відновлювалися правильно.

### 9. Що роблять @Retention(RUNTIME) і @Target(FIELD)?

`@Retention(RUNTIME)` означає, що анотація доступна під час виконання програми, зокрема через рефлексію. `@Target(FIELD)` обмежує використання анотації полями класу.

### 10. Чому анотація не виконує експорт сама?

Анотація є метаданими, а не алгоритмом. Вона описує поля, які потрібно експортувати. Саме `CsvExporter` читає ці метадані, отримує значення полів і формує CSV-файл.

### 11. Чим getDeclaredFields() відрізняється від отримання публічних полів?

`getDeclaredFields()` повертає поля, оголошені безпосередньо в класі, зокрема непублічні, але не включає успадковані поля. `getFields()` повертає доступні публічні поля класу та його суперкласів.

### 12. Навіщо перевіряти trySetAccessible()?

`trySetAccessible()` дає змогу перевірити, чи вдалося відкрити доступ до поля або іншого члена для рефлексивної операції. Якщо доступ неможливо отримати, програма може обробити проблему явно, а не несподівано завершитися помилкою.

### 13. Чому порядок полів для CSV потрібно зробити детермінованим?

Порядок полів, отриманих через рефлексію, не слід використовувати як неявну гарантію формату. Детермінований порядок забезпечує повторювані файли, стабільні тести й правильне зіставлення стовпців під час імпорту.

### 14. Чому split(",") не підходить для загального CSV?

Кома може бути роздільником стовпців, але також може входити до значення в лапках. Простий `split(",")` не враховує лапки, екранування та перенесення рядків, тому може неправильно розділити запис.

### 15. Як екрануються кома, лапка й перенесення рядка в CSV?

Поле, що містить кому, подвійну лапку або перенесення рядка, береться в подвійні лапки. Подвійна лапка всередині такого поля подвоюється. Наприклад, текст `новий "модуль"` записується як `"новий ""модуль"""`.

### 16. Чому порожній список потребує окремого параметра Class<T>?

Коли список порожній, неможливо визначити тип об'єкта через перший елемент. `Class<T>` може передати інформацію про тип явно. Це особливо корисно, коли потрібно отримати метадані класу для формування заголовка навіть без рядків даних. Такий параметр необхідний лише тоді, коли його передбачає API конкретного експортера.

### 17. Чим універсальний експортер відрізняється від предметного fromCsv?

Універсальний експортер використовує загальні правила, анотації та рефлексію, щоб перетворювати об'єкти на CSV без жорстко заданого переліку полів конкретного класу. Предметний `fromCsv` зазвичай знає структуру певного класу та вручну перетворює стовпці на його поля.

### 18. Які рівні помилок розрізняє програма?

Потрібно розрізняти щонайменше помилки файлового введення-виведення, помилки структури CSV, помилки перетворення типів і помилки допустимості значень. Власний виняток може надати єдиний контекст для CSV-помилок, зберігаючи початкову причину.

### 19. Що доводить тест round-trip?

Round-trip тест перевіряє узгодженість експорту й імпорту. Якщо після послідовності «об'єкти → CSV → об'єкти» відновлені значення відповідають початковим, це підтверджує правильність роботи з полями, порядком стовпців, екрануванням і перетворенням типів для перевірених випадків.

### 20. Чому виняток не можна поглинати порожнім catch?

Порожній `catch` приховує помилку й не дозволяє викликачеві зрозуміти, що операція завершилася невдало. Це може призвести до неповних файлів, втрати даних або некоректного результату без пояснення. Помилку потрібно обробити, передати далі або обгорнути у виняток із збереженням початкової причини.
